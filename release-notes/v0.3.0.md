Ymir is a node-based procedural terrain generator for Linux. You build terrain by wiring nodes
together, watch it in a 3D viewport, and export heightmaps for a game engine or a DCC package.

This release makes the headless runner useful: it renders your own projects, not just a built-in
sample. Getting there needed a change to the project file, which is why it does not open v0.2
projects.

## Read this first: v0.2 projects do not open

The project file changed shape and will not load in this version. There is no migration.

In v0.2 the world settings lived in a section only the editor read. A `.ymir` file said what the
node network was, but not what world it described, so nothing outside the editor could reproduce
the terrain. The seed, world size, height, sea level, and build resolution now sit in the file's
own top-level `world` section, where anything reading the file can find them.

Opening a v0.2 project reports its version rather than loading part way. If you have projects you
want to keep, stay on v0.2 until you have rebuilt them, or [open an
issue](https://github.com/liminalfield/ymir/issues) and a converter can be written.

The format is documented at
[Project format](https://liminalfield.github.io/ymir/reference/project-format/).

## Render a project from the command line

```
ymir-cli render coast.ymir --out height.png
```

The seed, world size, and build resolution come from the project file, so a headless render
produces what the editor shows rather than the same node network under different settings.
Erosion runs on the GPU when a device is reachable and falls back to the CPU otherwise.

What gets built is the project's result nodes, which is what Build means in the editor. A project
ending in export nodes needs no `--out`, since each export writes the path it carries, and an
export switched off for builds stays off. A project ending in an ordinary node, which is the usual
shape for one saved while working, has no path of its own, so `--out` names the file. The format
follows the extension: `.png` and `.r16` are 16-bit, `.exr` is 32-bit float.

`--res N` builds at N cells square instead of the project's own build resolution. `--node NAME`
builds one node, by its editor name or its stable id, instead of every result node.

A render that cannot do what was asked exits non-zero and writes nothing.

## Smaller changes

- `ymir-cli --help` prints the usage, and an unrecognised argument is an error with exit status 2
  rather than a silent fall-through to the sample render.
- The editor and the headless runner now build their evaluation requests through one constructor,
  so the two cannot disagree about what world a project describes.

## Requirements

Linux, on Wayland or X11, and a Vulkan-capable GPU with working drivers. The viewport runs on
Vulkan through wgpu and the editor will not start without it.

## Install

Download `ymir-gui-linux-x86_64`, make it executable, and run it:

```
chmod +x ymir-gui-linux-x86_64
./ymir-gui-linux-x86_64
```

`SHA256SUMS` accompanies the binaries if you want to verify the download. `ymir-cli-linux-x86_64`
is the headless runner.

Building from source is described in the
[install guide](https://liminalfield.github.io/ymir/install/).

## Known limits

- **Linux x86_64 only.** There are no Windows or macOS builds.
- **A preview is not a build.** Erosion is an iterative simulation, so it is resolution-dependent:
  a preview is representative of a build rather than identical to it. The build is the source of
  truth.
- **The save format is not stable yet.** This release breaks it, as described above. Ymir is in
  `0.x` and makes no compatibility promise until 1.0.
- **There is no tutorial yet.** The reference is complete, with a page per node, and a
  start-to-finish walkthrough is still to be written.

## Documentation

The manual is at [liminalfield.github.io/ymir](https://liminalfield.github.io/ymir/): concepts,
how-to pages, and a reference page for every node. The tutorial is a placeholder, not a
