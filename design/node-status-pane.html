One node pane, three states

A single dock pane listing every node in the graph and what each one is doing. It replaces two planned panes, a node outliner and a build list, with one view. Rows never reorder: the left half of a row is identical in every state, and only the trailing slot changes. Fake data, real palette, real typeface, real node names.

Two renderings, two fidelities

The canvas and the pane draw the same status model at different weights. A node header carries the dot and nothing else, so the graph stays readable at a glance; the pane carries the glyph, the word and the detail. Neither is the other's legend, and only the pane needs to be read.

Settled

Decided in review, and drawn above rather than described.

  1. One pane, not two. Rows never reorder, and a row's left half is identical in every state. Only the trailing slot changes, so nothing moves under you when a build starts.
  2. Canvas and pane both, at different fidelity. Node headers keep the dot alone; the pane carries glyph, word and detail.
  3. Outputs stays the source of truth for build inclusion. The pane's build chip mirrors it, on the same two-controls-one-value pattern as the viewport's output picker.
  4. Dependency order always, in every state, with an explicit user sort for canvas order, alphabetical, or stale first. Sorting is a choice you make, never one the state makes for you.
  5. Large graphs get collapsible subgraph groups, a filter field with stale, failed and endpoint quick chips, and a compact one-line density.
  6. Elapsed time only, plus a percentage for the nodes that report one. No build-level estimate, because it would be extrapolation and wrong exactly when it matters.

What this costs to build

Most of the pane needs no engine work. Only the live build picture does: one observational seam, plus opt-in reporting from the slow operators.

Idle and after-build available today

Graph::cache_status already returns current-versus-stale for every node in a pull without evaluating anything. Bypass, pinning, wiring and build inclusion are readable from the graph. Build availability is the field-store lookup the viewport's source toggle already does.

Queued, active, done engine seam

The evaluator computes nodes one at a time in dependency order and emits nothing. It needs an optional progress sink, notified as each node starts and finishes. Purely observational, so determinism is untouched.

Percentage within a node operators opt in

A bar inside a node means the operator reports fractional progress, such as erosion's iteration i / N. Nodes that do not report show elapsed time and a barber pole, never an invented percentage.

Left for the design pass

Smaller than it was, and all of it visual rather than structural.

  • What the compact row drops. It hides the type id here, which makes two nodes of the same name harder to tell apart. Hover, a suffix, or something else.
  • What a collapsed group summarises. A count is the minimum; the worst state inside it may matter more than the number.
  • How the trailing slot handles crowding. A pinned, built, stale endpoint wants four marks in a slot about ninety pixels wide.
  • Whether the filter and sort persist across sessions, or reset with each project open.
  • How the active row reads without motion. The barber pole is the only animated thing here, and it should still work for a viewer with reduced motion set.
